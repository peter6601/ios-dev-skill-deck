AI-REVIEW · 號誌與閘門開場

起點 · WHY

AI 可以互相檢查，
但不會替人類放行。

讓另一家模型來審，看到的盲點不同；可是 Codex 說 PASS，也不代表就是對的。
所以這條線的最後一道閘門，永遠留給人。

AI-REVIEW · 號誌與閘門文件審查

一次審一種角度：lens

requirement

需求規格

有沒有洞？

沒寫到的行為、沒定義的邊界、沒人測得了的驗收條件。

direction

設計文件

方向對嗎？

它排除了什麼、有沒有更便宜的做法、是不是在解沒人有的問題。

implementation

實作規格

跟現有 code 對得上嗎？

它假設的名稱、契約、呼叫點，和悄悄矛盾的地方。

一份檔案其實是兩份文件，就審兩次；參考資料最多 5 段、16,000 tokens，要指到精確的章節。

01

Repo

02

Base

明確給，不猜 main、HEAD 或 merge base

03

Brief

一兩句話：這個改動原本要做到什麼

04

Profile

ios 或 generic，建立前先講給你聽

05

聚焦的驗證指令

至少一個針對這次的測試；不接受冒煙測試、整包測試頂替

06

iOS preflight

三個 specialist 的 findings，init 時一起交

缺什麼就問人，不從 branch 或 diff 猜。

AI-REVIEW · 號誌與閘門程式碼審查

聯鎖 · INTERLOCKING

路線一變，
號誌就失效。

核准綁定當下的 base 與完整 patch；code 一改，舊核准就作廢。
claude、codex 的執行檔在建立時記下指紋；
驗證指令不經 shell，只允許可信任路徑上的工具。

AI-REVIEW · 號誌與閘門實測

坑 1

規則對，交接的形狀錯了

改之前

29 個 iOS 審查卡在「等 preflight」，0 次交成功

怎麼改

改成建立 run 時一起交：三個 specialist 各吐一段 JSON，主 session 只負責包起來。

改之後

之後 10 個審查有 9 個帶著 preflight 開跑

三個 specialist 的報告要在 run 開始後，由人手組成一份七個欄位都不能錯的 JSON 再交；錯了就 exit 2。驗證器沒寫錯，是交接的形狀錯了。

AI-REVIEW · 號誌與閘門實測

坑 2

閘門被挪動，run 就停死

改之前

114 個 run 有 31 個（27%）停在「審查門檻被移動」

怎麼改

finding 帶上有型別的來源（已存在／修出來的／新發現），產生時就被 schema 強制。

改之後

之後 23 個 run，0 次

判斷「這是新問題還是修出來的問題」靠比對 finding 的英文字串，而且從沒告訴 Codex 有這個約定。

AI-REVIEW · 號誌與閘門實測

坑 3

讓 AI 修文件，反而走不到終點

改之前

舊 plan 模式 49 個 run，只有 1 個走到人工審查

怎麼改

拿掉自動修復：Codex 只讀審查，人取捨後，Claude 才改被採納的那幾條。

改之後

文件審查 15 個 run，10 個走到人工審查

審完由 Claude 自動修文件、再審：外部呼叫失敗和「門檻被移動」大多卡在修復這一側。
